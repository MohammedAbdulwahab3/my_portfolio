# memforge benchmark results

Generated by `bench/run_benchmarks.sh build WORKDIR 2G` on a 4-core cloud VM. The 2 GiB image is synthetic (`mkimage --copies 64`): 30% zero pages, 20% prose, the rest code-like bytes. That mix produces an unusually high string density (9.4 M strings), which makes `strings` and JSON output the dominant cost.

## Notes

* **Section 1.** Every thread count produces the same finding count, and the
  test suite checks that the output bytes match too. Scaling is near-linear
  because chunks are independent, JSON is rendered on the worker threads, and
  only the ordered append is serial.
* **Section 2.** `pescan` probes only page-aligned offsets, so it is bound by
  page-cache bandwidth, not compute. Its 4-thread figure is noisy.
* **Section 3.** The Python baseline uses the C-implemented `re` module over
  `mmap`, which favours Python. Its ASCII string count (9,369,076) matches
  memforge's `strings.ascii` counter, so both do the same work.
* **Section 4, window.** `window=1` scans images one by one. A 16 MiB image is
  a single 16 MiB chunk, so only one core works. `window=16` flattens
  (image, chunk) tasks across images.
* **Section 4, dynamic farm.** Rank 0 is a dedicated coordinator, and Open
  MPI's blocking receive busy-polls. On this 4-core box the coordinator
  therefore steals a core from the workers. On a cluster it sits on a login or
  head node, or the static LPT schedule is used. Dynamic scheduling pays off
  when image sizes or node speeds are uneven.
* **Section 4, split.** On one node, `split` matches the local run, showing the
  rank decomposition and ordered merge add negligible overhead. Its purpose is
  multi-node runs on images too large for one node to scan quickly. Cross-node
  scaling is not measured here.
* All MPI runs use `--bind-to none`. With Open MPI's default per-core binding,
  `split` at 2 ranks × 2 threads took 12.0 s instead of 3.4 s.
